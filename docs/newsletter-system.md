# メルマガの仕組み（設計と運転）

名刺交換でいただいた連絡先に、不定期の便り（**OZAKEN LETTER**）を届けるための一式。
**送信そのものは Resend に任せ、名簿・配信停止・記録はこちらで持つ。**

配信停止は `https://content.ozaken.ai/unsubscribe` で受ける。
資料アーカイブと同じ Cloudflare Pages の上に、Functions として同居している。

---

## 1. なぜ自前で全部やらないか

メールは「送れば届く」ものではない。2024年2月から Gmail と Yahoo が
一括送信者に課している条件がある。

| 条件 | 誰が満たすか |
|---|---|
| SPF / DKIM / DMARC で送信元を証明する | Resend（ドメイン認証を1回やる） |
| ワンクリックで配信停止できる（`List-Unsubscribe` ヘッダ） | このリポジトリの `functions/unsubscribe.js` |
| 迷惑メール報告率を 0.3% 未満に保つ | 報告された人を即座に外す仕組み（`functions/api/hooks/resend.js`） |
| 宛先不明を放置しない | 同上（バウンスの自動処理） |

自前の SMTP で送ると、最初の1通目から迷惑メールに落ちる。
IPの評判を育てるところから始めることになり、割に合わない。

一方で、**名簿を配信サービスに預けっぱなしにもしない。**
乗り換えのたびに配信停止の履歴が飛ぶと、一度断った人にまた送ってしまう。
名簿と「止めた記録」は D1 に置いて、こちらで持ち続ける。

## 2. 層構造

```
名刺管理サービス（Eight / Sansan）
   │  CSVで書き出す ── **ここだけ手作業。Eightに公開APIがないため（5-6）**
   ├──→ roster.html（ブラウザに落とす。下見してから入れる）
   └──→ newsletter/import_meishi.py（端末から。大きいCSV向け）
   │
   ▼
Cloudflare D1「ozaken-newsletter」          ← 名簿の正本。ここが「正」
   │  subscribers / issues / deliveries / events
   ▼
functions/api/send.js（分割配信）
   │
   ▼
Resend API  ──→  受信者
   │                 │
   │                 ├─ 本文の「配信を停止する」        ┐
   │                 └─ Gmail の「配信停止」ボタン      ├→ functions/unsubscribe.js → D1
   │                                                     ┘
   └─ バウンス・迷惑メール報告 → functions/api/hooks/resend.js → D1
```

## 3. 配信停止の作り

ここがいちばん間違えやすいので、先に書く。

### 署名つきURL

```
https://content.ozaken.ai/unsubscribe?e=<アドレス>&s=<HMAC-SHA256の署名>
```

`e=` だけだと、他人のアドレスを打ち込んで勝手に解除できてしまう。
`NEWSLETTER_SECRET` を鍵にした署名を添えて、**こちらが発行したリンクだけ**を受け付ける。
署名には用途（`unsub` / `confirm`）を混ぜてあるので、確認用のリンクを配信停止に使い回せない。

### GET では絶対に止めない

企業のメールセキュリティ製品は、本文中のリンクを勝手に開いて安全確認する。
**GETで即解除にすると、本人が押していないのに配信が止まる。**
だから GET は確認画面を出すだけにして、POST で初めて止める。

### ワンクリック配信停止

`List-Unsubscribe` と `List-Unsubscribe-Post` の2本を送ると、
Gmail は件名の横に「配信停止」ボタンを出す。押されると、こちらの
`/unsubscribe` に **POST** が飛んでくる（本文は `List-Unsubscribe=One-Click`）。
相手はHTMLを読まないので、この場合だけ素の `200` を返す。

### 一度止めた人を復活させない

これを守れないと、断った相手にまた送ることになる。3か所で効かせている。

- **取り込み**：`ON CONFLICT` で `status` に触らない。
  同じCSVを何度流しても、止めた人は止まったまま（名前と会社名だけ新しくなる）。
- **確認リンク**：停止後に古い確認メールのリンクを踏んでも `active` に戻さない。
- **配信の宛先選び**：`status = 'active'` だけを引く。

## 4. 法令まわり（特定電子メール法）

### 送っていい相手

原則はオプトイン（事前の同意）。ただし例外があり、
**名刺などで相手が自分から連絡先を通知してきた場合**は、同意なしで送れる
（施行規則の明文）。名刺交換でいただいた相手は、ここに乗る。

Webからの申し込みは、ダブルオプトイン（確認メールのリンクを踏んで初めて登録）にしてある。
他人のアドレスを勝手に登録するいたずらを、これで無効化できる。

### 本文に必ず載せるもの（表示義務）

`functions/_lib/mail.js` のフッターが、常に次を出す。抜くと違反になる。

- 送信者の氏名・名称 … `NEWSLETTER_SENDER_NAME`
- 送信者の住所 … `NEWSLETTER_SENDER_ADDRESS`
- 受信拒否の通知先 … 配信停止リンク
- 苦情・問い合わせ先 … `NEWSLETTER_REPLY_TO`

住所を出すのが難しければ、バーチャルオフィスや事務所の住所を使う。
**空欄にはしない。**

### 資料ダウンロードから来た人（index.html のリードゲート）

トップページの資料ダウンロードは、お名前・会社名・メールアドレスを取ってから
資料を出す（`index.html` の `#leadGate`）。

**送り先は 2026年8月に Apps Script から `/api/download` に移した。**
それまでは Google スプレッドシートに貯め、`aicx.jp` からお礼メールを出していた。
差出人ドメインが2本あると、次に届くお便りが「知らない相手」に見えて、
配信停止ではなく迷惑メール報告に向かう。`news.ozaken.ai` に寄せた。

> **Apps Script 自体は止めていない。** 同じスクリプトが
> 質問・コメントの投稿（`ask.html`）と読み出し（`index.html` の投影Q&A、
> `inbox.html`）も担っている。止めると登壇中のQ&Aが死ぬ。
> 資料ダウンロードの経路だけを切り離してある。

`/api/download` は、ゲートの注記を同意の根拠として `events` に丸ごと残し、
その場でお礼メール（`buildWelcome`）を出す。**一度配信停止した人には送らない。**
ゲートはこの呼び出しが失敗しても資料を出す ── 受け口の不調でダウンロードが
止まるのがいちばん困るので、`/api/download` は常に `ok` を返す。

**同意はここで取っている。** 文面は2026年8月に直した。

> いただいたメールアドレスには、**小澤健祐（おざけん）およびAICX協会から**、
> AIに関するメールマガジン（不定期・月1〜3通ほど）と、講演・顧問のご案内をお送りします。
>
> 送信をもって、小澤健祐（おざけん）およびAICX協会からのメールマガジン・資料・
> イベント案内の受け取りにご同意いただいたものとします。

**直した理由は、同意の名義と送信者の名義がずれていたから。**
以前は「AICX協会からの資料・イベント案内」としか書いていなかった。
特定電子メール法のオプトインは「誰から送られるか」を含めて同意を得る前提なので、
協会名義で取った同意で、おざけん個人名義のメルマガを送るのは範囲外と見られうる。

「利用させていただく**場合があります**」も「お送りします」に改めた。
曖昧に書くと、届いたときに「聞いていない」となって迷惑メール報告に向かう。

> **AICX協会名義で送るときは、表示義務の中身も協会のものに差し替える。**
> `NEWSLETTER_SENDER_NAME` / `NEWSLETTER_SENDER_ADDRESS` / `NEWSLETTER_REPLY_TO` は
> いま1組しか持っていない。協会名義の号を出すなら、ここを切り替える仕組みが要る。

**2026年8月より前に集まった分**は、協会名義だけの同意で取れている。
厳密には範囲外だが、資料請求というやりとりの中で本人がアドレスを通知してきた
相手なので、名刺と同じ考え方が使える余地がある。取り込むときの「取得の場」に
`AICX協会名義で取得` と書いて記録に残し、1通目で経緯を明示する
（`source='download'` の一文が自動で入る）。

### 記録の保存

`events` 表に、同意・確認・配信停止・バウンス・苦情を消さずに積んでいる。
`subscribers.consent_at` には名刺交換日（CSVから拾えたもの）が入る。
「いつ・どこで連絡先をいただいたか」を、あとから示せる状態にしてある。

## 5. 立ち上げの手順

### 5-1. Resend でドメインを認証する（済）

送信ドメインは **`news.ozaken.ai`**（東京リージョン）。2026年8月28日に認証済み。

**ルートの `ozaken.ai` ではなくサブドメインを切ってある。**
メルマガの評判とドメイン本体の評判を、同じ籠に入れないため。
迷惑メール報告が増えても、ふだんのやりとりのメールは巻き込まれない。

DNS は Cloudflare にあるので、Resend の Auto configure でレコードを入れた。
入れ直すときも同じ手が使える（DKIMの公開鍵は長く、手で写すと必ず事故る）。

> **Cloudflare で手を入れるときの落とし穴**
> - プロキシ（オレンジの雲）は必ずオフ＝ DNS only。CNAME や MX がオレンジだとメールが壊れる
> - Name 欄にはサブドメイン部分だけを書く。`.ozaken.ai` を足すと二重になる

**DMARC はドメイン本体（`_dmarc.ozaken.ai`）に置く。** サブドメインは親を継承する。
`p=none` から始めること。いきなり `p=reject` にすると、Google Workspace など
別の経路で出しているメールまで巻き添えで弾かれる。

### 5-2. D1 を作る

```bash
npx wrangler d1 create ozaken-newsletter
# 出力された database_id を控える
npx wrangler d1 execute ozaken-newsletter --remote --file=newsletter/schema.sql
```

Cloudflare のダッシュボードで、Pages プロジェクトに束ねる。

> Workers & Pages → ozaken-materials → Settings → Bindings → D1 database
> Variable name: `DB` ／ D1 database: `ozaken-newsletter`

**`wrangler.toml` をリポジトリ直下に置かない。** ダッシュボードの設定を上書きして、
いま動いている静的配信を壊しかねない。見本は `newsletter/wrangler.sample.toml` に置いてある。

### 5-3. 環境変数を入れる

同じ Settings → Variables and Secrets に。**Secret（暗号化）** で入れるもの:

| 名前 | 中身 |
|---|---|
| `NEWSLETTER_SECRET` | 配信停止リンクの署名鍵。`openssl rand -base64 36` で作る |
| `NEWSLETTER_ADMIN_TOKEN` | `/api/send` を叩くための鍵。同上 |
| `RESEND_API_KEY` | Resend の `re_...` |
| `RESEND_WEBHOOK_SECRET` | Resend の Webhooks 画面に出る `whsec_...` |

**Text（平文）** で入れるもの:

| 名前 | 例 |
|---|---|
| `NEWSLETTER_SITE` | `https://content.ozaken.ai` |
| `NEWSLETTER_FROM` | `小澤健祐（おざけん） <ozaken@news.ozaken.ai>` |
| `NEWSLETTER_SENDER_NAME` | `小澤健祐（おざけん）` |
| `NEWSLETTER_SENDER_ADDRESS` | 登記上の住所 |
| `NEWSLETTER_REPLY_TO` | **実際に受信できるアドレス**（下の注意を読む） |
| `NEWSLETTER_UNSUB_MAILTO` | 同上（任意） |

`NEWSLETTER_SECRET` は**あとから変えない。**
変えると、すでに配ったメールの配信停止リンクが全部無効になる。

> **`news.ozaken.ai` に受信箱はない。**
> 差出人の `ozaken@news.ozaken.ai` に返信されても、どこにも届かない。
> `NEWSLETTER_REPLY_TO` には**必ず、実際に読んでいるアドレス**を入れる。
> ここを空にすると、返信が宛先不明で跳ね返る ── 相手には「無視された」ように見える。
> `NEWSLETTER_UNSUB_MAILTO` も同じで、受信できないアドレスを書くくらいなら空にする。

### 5-4. バウンスの受け口をつなぐ

Resend の Webhooks で、次のURLを登録する。

```
https://content.ozaken.ai/api/hooks/resend
```

拾う出来事：`email.bounced` と `email.complained`。

### 5-5. 名簿を入れる

`https://content.ozaken.ai/roster.html` を開き、管理者トークンを貼って、CSVを落とす。
（端末から流し込む道も残してある。下の「5-7」を見る。）

## 5-6. Eight から自動で取れないか

**個人版の Eight に公開APIはない。** 完全な自動化はできない。
分かっていることを、はっきり書いておく。

| | 自動でできるか | 実際のところ |
|---|---|---|
| Eight（個人版）のAPI | ✕ | 公開されていない。Sansan が API を出しているのは**法人向けの Sansan** の方 |
| Eight（個人版）のCSV書き出し | △ | できるが**手作業**。Eightプレミアム（月480円／年4800円）が要る。PC版のみ |
| Eight Team（法人版） | △ | 共有名刺の一括ダウンロード。kintone / HubSpot とは直接つながる |
| Sansan（法人版） | ○ | 期間や条件を指定して名刺情報を引ける API がある |

Eight のCSVは、PC版で **設定（歯車）→ 名刺のダウンロード → ダウンロードファイルを作成**。
作られたファイルはリンクで渡され、**24時間で消える**。

つまり、いま消せない手作業は「Eightでボタンを押して、できたCSVを落とす」ここだけ。
そこから先 ── 文字コードの判定・列の読み取り・重複の除去・
配信停止済みの人を触らないこと・記録を残すこと ── は `roster.html` が全部やる。

**自動化したくなったら、Sansan（法人版）に移るのが唯一まっすぐな道。**
API があるので、定期的に引いて名簿に流し込むところまで作れる。
Eight のままブラウザ操作を自動でなぞる（スクレイピング）のは、
利用規約の面でも、画面が変わるたびに壊れる面でも、勧めない。

### roster.html でやること

1. 管理者トークンを貼る（このブラウザにだけ憶える。サーバーには置かない）
2. 「取得の場」を書く（例：`2026年上期 名刺交換`）。記録として名簿に残る
3. CSVを落とす → **まず下見が走る。この時点では名簿に何も書かない**
4. 下見の中身を見る
   - 読み取った列が合っているか（`email → メールアドレス` など）
   - 新しく入る件数、すでにいる件数
   - **配信停止済みで手を触れない件数** ── ここに数字が出たら、それは正しい動き
5. よければ「この内容で取り込む」

文字コードはブラウザ側で判定する。まず UTF-8 として厳密に読み、
弾かれたら Shift_JIS として読み直す（Eight の書き出しは Shift_JIS のことがある）。

行数が多いCSVは、自動で分割して何度か送る。途中で止まっても、
同じCSVをもう一度落とせば、入った分はそのままに続きから入る。

### 5-7. 端末から入れる（大きいCSV・自動化したいとき）

```bash
python3 newsletter/import_meishi.py ~/Downloads/meishi.csv \
  --source-note "2026年上期 名刺交換" \
  -o newsletter/import.sql

npx wrangler d1 execute ozaken-newsletter --remote --file=newsletter/import.sql
```

`roster.html` と同じ結果になる（列の見出しの候補は `selftest.mjs` がそろっているか見張っている）。

- 文字コードは cp932 と UTF-8 の両方を試す。
- **見出しを信じきらない。** 書き出しの途中で項目が増えると、見出しはそのままに
  中身だけ1つずれることがある。実際、資料ダウンロードの記録1,240行のうち
  **1,129行で「氏名」の列にアドレスが入っていた**。見出しだけで判断していたら
  9割を黙って捨てていた。アドレスは行の中身から探し直し、名前が入れ替わって
  いれば戻す。`selftest.mjs` の13番が、この形を再現して見張っている。
- 「資料」の列があれば、行ごとに「どの資料から来たか」を残す。
- 重複・形式不正は落とし、件数を最後に出す。
- 送りたくない相手は `--exclude` にファイルで渡す（1行1アドレス）。
- **CSVと `import.sql` は個人情報なので、リポジトリに入れない**（`.gitignore` 済み）。

## 6. 号の出し方

### この名簿がどういう人たちか（2026年8月時点・1,131件）

**運用の判断は、全部ここから出る。**

| | |
|---|---|
| どこから来たか | 資料ダウンロード。**89%が「AIエージェント実装の5レベル」1本** |
| 誰か | **独自ドメイン 930件（82%）**。116社では複数人が同じ資料を落としている（社内で回覧されている） |
| いつ | 2026-07-29〜08-28 の30日で集まった。**直近7日はわずか53件（4%）** |

ここから決まること。

1. **単一テーマの名簿である。** 全然違う話題を送ると「頼んでいない」になる。
   1通目は、あの資料の続きにする。
2. **読み手は組織で動かす立場の実務者。** 勉強したい個人ではない。
3. **大半が3〜4週間前の接触。** 時間が経つほど「誰これ」になって迷惑メール報告に変わる。**早く出す。**

### 管理画面（roster.html）

**トップページで `nl` と打つと開く。** スマートフォンは右下の隅を長押しして、
隠しメニューの NL から。`index.html` の `CODES` と `run()` の両方に入っている
（片方だけだと、打っても何も起きない）。

鍵は管理者トークン1本。暗号化した資料ページとは違うので、
ページ自体には鍵をかけていない ── 中身は全部APIの向こう側にある。

| 面 | 中身 |
|---|---|
| **概況** | 名簿の内訳、直近7日の動き、最近の出来事（配信停止・宛先不明・迷惑報告） |
| **号** | これまでの号と成績、前号を下敷きにした複製、号を書く、配信 |
| **名簿** | 名刺・資料ダウンロードのCSV取り込み、動作確認のメール |

苦情率が 0.3% を超えた号は、一覧で赤く出る。**Gmail に届かなくなる線。**

### 号を書く／送る

端末は要らない。「号」の面の「号を書く」に入力して、

1. **見え方を確かめる** … `/api/preview` が**実際に送るのと同じ関数**で組み立てて返す。
   本文の組み立てを画面側に持たないので、「プレビューでは合っていたのに違うものが届いた」が起きない
2. **この号をテスト送信** … 自分に1通。名簿にも配信ログにも残らない。**実機で必ず確かめる**
3. **配信をはじめる** … 下の段階配信へ

下書きはブラウザに憶えるので、書きかけで閉じても消えない。

### 段階配信 ── いきなり全員に送らない

**新しい送信ドメインが突然1,000通を超えて送るのは、迷惑メール判定でいちばん疑われる形。**
Resend は束の中の1通ごとに配達時刻を持てる（30日先まで）ので、
**一度の投入で「初日75通、翌日151通…」を予約できる。**

既定は4日、日を追うごとに倍。1,131件なら 75 / 151 / 302 / 603。
途中で苦情率が跳ねたら、そこで止められる。一度に送ると、気づいたときには全部終わっている。

**土日は自動で飛ばす。** 名簿の8割が法人のアドレスで、土日に届けても月曜の受信箱に埋もれるだけ。

> **予約したあとの取り消しは1通ずつ。** だから「テストで確かめた」に印を付けるまで、
> 配信のボタンは押せないようにしてある。

### 定常運用

| | |
|---|---|
| 頻度 | **月2回**を目安（購読ページの約束は月1〜3通なので余裕がある） |
| 曜日・時刻 | **火〜木の朝8時台**。月曜は溜まったメールに埋もれ、金曜は流される |
| 主指標 | **返信数**。開封率は Apple のプライバシー保護で当てにならない |
| 見張る数字 | 苦情率 **<0.1%**（0.3%でGmailに届かなくなる）／バウンス率 **<2%** |

苦情率が上がったら、送る相手か文面を疑う。**送る頻度を上げて解決する問題ではない。**

### 図版を入れる

**メールの画像は、Webの画像とは別物。**

| | |
|---|---|
| **SVGは載せられない** | Gmail をはじめ多くが剥がす。資料の図版は **PNGに焼いてから**置く（`shot_figs.mjs`） |
| **data: URI も剥がされる** | 公開URLに置く。`99_assets/letter/YYYY-MM-DD/fig1.png` |
| **既定で表示されないことがある** | Outlook など。**`imageAlt` は必須**（無いと送信を受け付けない） |
| **透明背景は暗い画面で浮く** | 紙色（`#f8f7f4`）を敷いてある |
| 高精細の画面 | 実体は表示幅の2倍（1064px）で書き出し、`width="532"` で表示 |

**いちばん大事な決まり：画像が1枚も出なくても、意味が通るように書く。**
図に語らせない。結論は必ず本文の文字にも書く。

置き場所は `content.ozaken.ai` のCDNなので追加費用はかからない
（`_headers` でキャッシュも指定済み）。

### 1通目にすること

**通常号として出さない。** 1,131人は誰もまだ1通も受け取っていない。

1. なぜ届いているか（資料をダウンロードいただいた経緯）
2. **5レベルの資料の続きを1本** ← これが本体。挨拶だけの号にしない
3. 今後お送りするもの
4. 不要ならここで止められること

ここで数十人抜ける。**それが正常で、狙い。** 抜けてもらったほうが苦情率が下がり、残った人が本当の名簿になる。

### 名前と頻度（決定済み）

| | |
|---|---|
| 名前 | **OZAKEN LETTER**（メール上部の帯に出る） |
| 差出人 | `小澤健祐（おざけん） <ozaken@news.ozaken.ai>` |
| 頻度 | **不定期。購読ページでは「月に1〜3通ほど」と伝えている** |

**`weekly@` にしなかったのは、出さない週があるたびに約束を破ることになるから。**
名前にも差出人にも頻度を入れていない。

ただし**不定期でも、最低で月1回は出す。** 3か月空くと、次に届いたとき
受け取った側は「誰だっけ」になり、そのまま迷惑メール報告に向かう。
書くことがない月は、短い号でいい。出さないより害が小さい。

購読ページ（`subscribe.html`）に書いた約束は、次の3つ。**破ると信用がすぐ減る。**

1. 前提が動いた論点だけを、数本
2. 図版つきの全文は資料アーカイブに（合言葉は購読者だけ）
3. 不定期。月に1〜3通ほど。営業の連絡に転用しない


### 号を書く

`newsletter/issues/YYYY-MM-DD.json` を作る。`sample.json` をコピーして中身を差し替える。

```json
{
  "id": "2026-08-25",
  "subject": "件名",
  "preheader": "受信箱の一覧に出る短い一文",
  "url": "https://content.ozaken.ai/weekly/2026-08-25.html",
  "passphrase": "週次ページの合言葉",
  "lede": "書き出し",
  "items": [{ "kicker": "分類", "title": "見出し", "body": "本文", "link": "https://…" }],
  "closing": "締めの一文"
}
```

**メールに図版は入れない。** 週次ページのHTMLをそのまま貼っても、
Outlook や携帯のメールアプリでは崩れる。メールはあらましだけにして、
図版つきの全文は暗号化した週次ページへ送る。合言葉は購読者だけに渡す
（`passphrase`）ので、これが購読していただく理由になる。

### 送る

```bash
export NEWSLETTER_ADMIN_TOKEN=…

# 1) まず自分に送って、実機で確かめる
./newsletter/send.sh --test k.ozaken1222@cinematorico.com newsletter/issues/2026-08-25.json

# 2) 本番
./newsletter/send.sh newsletter/issues/2026-08-25.json
```

`/api/send` は1回につき 500件しか送らない（Workers の実行時間と Resend の
レート制限のため）。`send.sh` が「残り0件」になるまで叩き直す。
**途中で止めても、同じコマンドを叩き直せば続きから再開する。**
誰に送ったかは `deliveries` に主キーで記録しているので、二重には届かない。

送信に失敗した相手は、次の周回で拾い直す（最大3回）。
3回でも送れなかった相手は最後に一覧で出るので、必ず目を通す。

### 状況を見る

```bash
curl -H "Authorization: Bearer $NEWSLETTER_ADMIN_TOKEN" \
  "https://content.ozaken.ai/api/send?issue_id=2026-08-25"
```

名簿の内訳（active / pending / unsubscribed / bounced / complained）と、
その号の配信結果が返る。

### 送ったあとに見るもの

- **迷惑メール報告率**（Resend のダッシュボード）。0.1% を超えたら、
  送る相手か文面を見直す。0.3% を超えると Gmail に届かなくなる。
- `complained` が増えていないか。増えているなら、名刺交換から時間が
  経ちすぎた相手に送っている可能性がある。

## 7. 直したら通すもの

```bash
node newsletter/selftest.mjs
```

D1 のかわりに `node:sqlite` を同じ形にかぶせて、`functions/` の実物をそのまま動かす。
Resend への送信は差し替えるので、**メールは1通も出ない**。

見ているのは、壊すと相手に迷惑がかかるところ。

- 署名のないリンク・他人のアドレスに付け替えたリンクで解除できないこと
- GET では止まらないこと（メールのリンク検査botが踏むため）
- Gmail のワンクリックで止まること
- **一度止めた人が、名簿の取り込み直しでも古い確認リンクでも復活しないこと**
- 同じ号が二度届かないこと
- 送信に失敗した相手を、次の周回で拾い直すこと（かつ無限ループしないこと）
- バウンスと迷惑メール報告で、名簿から外れること
- 本文に住所と問い合わせ先と配信停止リンクが必ず載ること（表示義務）
- 名刺CSVの引用符・改行・重複を正しく読むこと
- 端末版（Python）とブラウザ版（JS）で、列の見出しの候補が食い違っていないこと

## 8. 決めてあること

| 論点 | 決定 | 理由 |
|---|---|---|
| 送信 | Resend | ドメイン認証・バウンス処理・ワンクリック停止を任せられる |
| 名簿の正本 | Cloudflare D1 | 配信サービスを乗り換えても、停止の履歴が残る |
| Webからの登録 | ダブルオプトイン | 他人のアドレスを勝手に登録されない |
| 名刺からの取り込み | そのまま `active` | 施行規則の例外に乗る。ただし初回から停止導線を出す |
| ダウンロードの同意名義 | おざけん＋AICX協会の併記 | 同意と送信の名義がずれると、同意の範囲外になる |
| 配信停止の反映 | 即時（D1を直接書き換える） | 「すぐ止まる」と書いた以上、止める |
| 送信ドメイン | `news.ozaken.ai`（サブドメイン） | 評判をドメイン本体と切り離す |
| 差出人と名前 | 頻度を含めない（`ozaken@` / OZAKEN LETTER） | 不定期なので、`weekly@` だと毎回約束を破ることになる |
| 一度止めた人 | 二度と `active` に戻さない | 取り込み・確認リンクの両方で塞いである |
| メールの図版 | 入れない | 崩れる。全文は暗号化した週次ページへ |

## 9. まだやっていないこと

- **開封・クリックの計測**。開封のために透明画像を仕込むと、
  Apple の Mail プライバシー保護で数字が当てにならない。入れるなら
  クリック計測だけにする。
- **配信の予約**。いまは手で `send.sh` を叩く。定時に出したくなったら
  Cloudflare Cron Triggers を足す。
- **Eight からの自動取得**。個人版に公開APIがないので、いまは無理（5-6）。
  Sansan（法人版）に移れば、API で定期的に引けるようになる。
